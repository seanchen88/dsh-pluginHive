# 写作进阶指南

> `create-skill` 的第二级披露：动笔前扫一眼、写完对着复查。核心原则在 SKILL.md 第 4 节，
> 这里是可照抄的模板与反例。

## 1. 为什么"解释 why"胜过"堆 MUST"

模型有很好的心智理论，理解动机的指令能被迁移到你没预料的场景；全大写的强制词只会让它机械执行、
遇到边界就失灵。判断信号：**当你发现自己在写"必须/绝不/ALWAYS/NEVER"时，先问为什么需要这条**，
把理由写进去代替命令。

```diff
- 绝不要在没跑测试的情况下提交代码。
+ 提交前跑测试：这套流程里最贵的事故是"看起来能跑"的代码进了主干，回滚成本远高于等一次 CI。
+ 所以先跑相关测试，全绿再提交；如果测试本身是坏的，先修测试或在提交说明里写明。
```

## 2. 输出格式：给模板而不是描述

```markdown
## 报告结构
始终使用这个骨架：
# <标题>
## 摘要
## 关键发现
## 建议
```

模板比"写一份结构清晰的报告"有效得多——它消除了格式上的不确定性，把模型的注意力留给内容。

## 3. 示例：输入 → 输出

```markdown
## 提交信息格式
**示例 1**
输入：新增了用户认证，使用 JWT
输出：feat(auth): 实现基于 JWT 的用户认证
```

示例要挑**边界清楚**的：一个典型、一个易错，比给五个相似例子更有信息量。

## 4. 三级披露的预算

| 层级 | 何时在上下文里 | 建议体量 |
|---|---|---|
| `name` + `description` | 永远 | ~100 词以内 |
| SKILL.md 正文 | 触发后 | < 500 行 |
| `references/` | 按指针读取 | 不限；单文件 > 300 行要带小目录 |
| `scripts/` | 只运行，不读入 | 不限 |

正文超预算时的做法：加一层目录（"做 X 类任务时读 `references/x.md`"），而不是把字变小或删掉有用细节。

## 5. `scripts/` 的判据

如果多次运行中模型都在**重新写同一段代码**（同样的解析、同样的图表、同样的多步转换），就该把它
固化成脚本放进 `scripts/`，并在正文里直接给出调用方式。收益是每次调用不必重造轮子，且行为可复现。

写脚本时：优先零依赖（用语言标准库），失败时给出可操作的错误信息，并在正文里说明预期输出。

## 6. 常见反例

- **把技能写成背景科普**：模型需要的是"下一步做什么"，不是领域百科。科普放 `references/`。
- **过拟合到手头例子**：为三个测试用例各加一条特判 → 换个真实请求就崩。改法：往上抽象一层。
- **description 只写"是什么"**：漏掉"什么时候用"，导致该触发时不触发。
- **description 写成用户手册口吻**：它是给模型的路由线索，不是给人看的产品文案。
- **一个技能想包办所有场景**：领域差异大时拆成多个技能或用 `references/` 分支。
- **窄到具体文件名/项目名**：除非技能本就是项目专属，否则写成通用的。

## 7. 写完的自查清单

- [ ] `description` 同时说清了"做什么"和"什么时候用"，并且列举了用户可能的说法。
- [ ] 正文祈使句为主，没有大段背景铺陈。
- [ ] 每条强约束都能回答"为什么"，否则改成解释。
- [ ] 至少一个输入→输出示例或一个固定模板。
- [ ] 引用的 `references/`、`scripts/` 文件真实存在，正文里说清了何时读/何时跑。
- [ ] 用 2–3 个"真实用户会说的话"试跑过，而不是只测理想提示。
- [ ] 跑过 `scripts/validate_skill.mjs` 且无 error。
