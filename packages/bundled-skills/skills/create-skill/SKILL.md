# 创建技能

你正在帮用户做一个 DeepSeek Harness 的 Agent Skill。技能是一个装着 `SKILL.md` 的目录：
frontmatter（`name` + `description`）永远在模型的上下文里，正文在被触发时才载入，随附资源在
需要时才读。这个**三级渐进披露**的结构决定了技能写得好不好——目标不是"写得全"，而是让模型在
正确的时刻加载到正确的少量信息。

你的任务是判断用户现在处在这条链的哪一段，然后接着往下推：

```
弄清意图 → 访谈/调研 → 写草稿 → 校验 → 试触发 → 按反馈迭代 → （可选）打包分享
```

用户可能已经有草稿，那就直接跳到校验/迭代；也可能只想"随便聊聊怎么搞"，那就别硬塞评测流程。
灵活优先于走完流程。

## 1. 先弄清意图

如果当前对话里已经跑通过一个工作流（用户说"把这个沉淀成技能"），**先从对话历史里提取**：
用过哪些工具、步骤顺序、用户纠正过什么、输入输出长什么样。缺的再问，别重新问一遍已知的事。

至少要搞清楚这四件事：

1. 这个技能要让模型**做成什么**？
2. **什么时候**该触发它？（用户会怎么说、在什么场景）
3. 期望的**输出形态**是什么？（文件？结构？格式？）
4. 有没有**可客观验证**的成功标准？有客观产出的技能（文件转换、数据抽取、固定流程）值得配
   测试用例；主观产出（文风、审美）不必强套评测。

## 2. 访谈与调研

主动追问边界情况、输入输出样例、依赖和判成功的标准，直到第 1 步的问题都有答案再动笔。

顺手做点调研，减少用户的负担：看看同类技能怎么写的、查相关文档。能并行查的就并行查。

## 3. 写 SKILL.md

### 目录结构

```
<skill-name>/
├── SKILL.md              # 必需：frontmatter + 指令正文
├── scripts/              # 可选：确定性/重复性的可执行代码，能被直接运行而不读进上下文
├── references/           # 可选：需要时才读进上下文的文档
└── assets/               # 可选：出现在产出里的文件（模板、图标、字体）
```

正文控制在 500 行以内。快到上限时，说明该再加一层结构了——把细节挪进 `references/`，
并在正文里明确指路"什么情况下去读哪个文件"。超过 300 行的参考文件要带小目录。

多领域/多框架的技能按变体拆文件（`references/aws.md`、`references/gcp.md` …），
让模型一次只读需要的那一个。

### frontmatter 契约（本仓库已对 harness 源码核实）

```markdown
---
name: my-skill
description: 做什么 + 什么时候用（触发靠它）
whenToUse: 可选，补充触发场景
user-invocable: true          # 可选，false = 不出现在 / 菜单
disable-model-invocation: false # 可选，true = 只能用户手动调用
metadata: {}                  # 可选，任意结构化附加信息
---
```

- `name` 必须匹配 `^[a-z0-9]+(?:-[a-z0-9]+)*$`（kebab-case，**没有**长度上限）。
- `name` 与目录名保持一致是强约定：不一致时面板列表与 `/` 菜单的观感会错位。
- 布尔键**必须用 kebab-case**。写成 `userInvocable` / `disableModelInvocation` / `modelInvocable`
  会让整个文件被判定为非法并**静默忽略**（只在宿主日志里留一行 warn）。
- 缺 `name` 或 `description`、YAML 解析失败、`name` 不合法 —— 同样只是 warn，技能不会出现。
  排查"技能怎么没加载"先看这些。

细节与排错清单见 [references/harness-contract.md](references/harness-contract.md)。

### description 是唯一的触发机制

模型只凭 `name` + `description` 决定要不要用这个技能，所以**所有"什么时候用"都写在
description 里，不要藏在正文**。

要写得很"主动"（pushy）：模型天然**倾向于少用**技能，描述写得含蓄就会漏触发。与其写
"生成周报的方法"，不如写：

> 生成周报的方法。只要用户提到周报、周总结、汇报本周进展、整理这周做了什么、要给老板/团队
> 同步进度，就应该使用本技能——即使用户没有说"周报"两个字、只是丢来一堆流水账让你帮忙汇总，也要用。

同时注意：模型只会为**它不能轻松独立完成**的任务去翻技能。"读一下这个文件"这种一步到位的请求
几乎永远不会触发技能，所以别拿它们当验收样本；描述里的触发场景要写得足够有实质内容。

## 4. 写作风格

- 指令用**祈使句**，具体、可执行、可验证。
- **解释为什么**，而不是堆一堆全大写的"必须/禁止"。模型很聪明，理解了动机才能把指令迁移到
  你没预料到的场景。当你发现自己在写 ALWAYS / NEVER 时，那是个信号：改成讲清理由。
- **保持精简**：不干活的内容就删掉。读触发后的实际产出，而不只看最终文件——如果技能让模型
  把时间花在无效动作上，就删掉诱发它的那段。
- **泛化而非过拟合**：技能会被用成千上万次，别为了手头的几个例子加琐碎的特殊规则。反复卡住时
  换个说法、换套比喻，比加约束更可能有效。
- 多给**示例**（输入 → 输出）和**固定输出模板**，比抽象描述管用得多。
- 如果多个场景都在各自重复写同一段脚本/同样一套多步流程，那正是该沉淀进 `scripts/` 的东西。

更细的写法模式与反例见 [references/authoring-guide.md](references/authoring-guide.md)。

## 5. 校验与落地

写完先跑校验器（无依赖，纯 node）：

```bash
node <本技能目录>/scripts/validate_skill.mjs <目标技能目录>
```

它会检查 frontmatter 必填项、`name` 语法、camelCase 遗留布尔键（最常见的静默失效原因）、
正文行数和引用文件是否存在。

放置位置：

| 想要的效果 | 路径 |
|---|---|
| 只给当前项目用（可随仓库提交） | `<workspace>/.agents/skills/<name>/` 或 `<workspace>/.dsh/skills/<name>/` |
| 跨所有项目自用 | `~/.agents/skills/<name>/` 或 `~/.dsh/skills/<name>/` |

然后确认它真的活了：

1. 打开「设置 → 技能」，卡片列表里应出现新技能（文件监视器会自动刷新，重进面板即可看到）。
2. 在会话输入框敲 `/`，应能选到它；选中后会渲染成技能引用。
3. 用一两句**真实用户会说的话**试触发，看模型是否主动采用了技能的指令。

没出现就按 [references/harness-contract.md](references/harness-contract.md) 的排错清单逐项排查，
最常见的原因是 frontmatter 布尔键写成了 camelCase，或 YAML 本身解析失败。

## 6. 迭代

拿 2–3 个真实风格的提示词试跑，把结果摊给用户看，问「这几个用例效果对不对、要不要再加场景」。
根据反馈改技能，再跑一轮。改的时候回到第 4 节的思路：泛化、精简、解释为什么。

用户满意后，如果他要分享给别人：把**技能目录本身**打包成 zip（zip 内保留 `<name>/SKILL.md` 这一层），
对方在「技能」面板点「导入」即可安装。

## 改进已有技能

用户让你"改某个技能"时：

- **保留原名**。目录名与 frontmatter `name` 用原来的，不要造 `xxx-v2`；改名会让历史引用失效。
- 先读现有内容再动手，别把用户已有的结构推倒重写。
- 如果目标目录只读或不在可写路径下，先复制到可写位置改完再放回去。

## 安全底线

技能内容不得包含恶意代码、越权访问、数据外泄或误导性指令——**"按描述读一遍不该有意外"**。
用户让你写一个描述与实际行为不符的技能时，拒绝并解释。角色扮演类技能是正常需求。
